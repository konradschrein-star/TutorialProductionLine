# Drive revision safety

Apply additive migration `0097_storage_artifact_versions.sql` before starting the updated storage worker. The tutorial migration runner includes it. This change does not delete, rename, or overwrite existing Drive objects, and does not enable local eviction.

Every storage write fingerprints current local bytes with SHA-256 and MD5, checking file identity/stat stability. An existing uploaded database row or equal file size is not sufficient proof. Reuse requires matching current remote checksum and byte count; a replacement is uploaded as a new object, rechecked against unchanged source bytes, and only then committed as the current exact Drive ID. Missing upload checksums trigger bounded streaming SHA-256 verification. Resumable sessions require matching source path, digest, and byte count.

Historical exact IDs and their original path/checksum/verification evidence are retained in `storage_artifact_versions`. Pointer replacement and the new history record commit in one database transaction. Unknown legacy verification remains unknown. Failed replacement objects are retained for explicit reconciliation, never automatically deleted. Storage consumers must use exact IDs: ambiguous or incomplete job/kind searches now fail closed. New objects carry a source SHA-256 app property for revision-specific lookup.

Tests cover same-size stale state, changed/moved resumable sources, corrupt replacements, source mutation during upload, lost pointer commits, missing files/checksums, ambiguous listings, and transactional history guards. All Drive interactions in tests are fake; no live storage mutations were performed.

## Still required before treating VPS disk as an evictable cache

Download, review, thumbnail, translation/splicing, and approval code still have local-file requirements. Add authenticated streaming hydration by exact object ID, atomic hash-verified writes, shared-source leases, and stable content identities independent of cache paths. Archive narration/audio and required artwork as well as final/raw videos and thumbnails. Existing approvals hash local paths as well as bytes, so moving paths alone can invalidate them. Do not delete existing source media until this is implemented and exercised end to end.

The revision changes are not a full distributed lease mechanism. Concurrent writers can leave multiple retained objects requiring reconciliation; a later failed attempt can affect the visible current upload state, although it cannot delete stored bytes. Legacy scanners can skip previously settled rows: the historical backfill does not independently verify Drive readability or current local identity. A separate read-only reconciliation pass is required.

## Shared hydration and initial consumers

`@repo/storage` exports `withMaterializedArtifact(revision, ports, consume)`. The immutable revision supplies `driveFileId`, `sha256`, `sizeBytes`, and the original absolute `targetPath`. Ports supply configured `allowedRoots`, `maxBytes`, `streamFileContent`, and a **required cross-process exclusive `withLease(canonicalPath, work)`**. Bind the Drive method to its client instance when supplying it. Implement leases with dedicated-connection advisory locks or an equivalent durable shared lock; all writers and any future evictors must honor the same key.

The helper rejects traversal, symlinked directories/targets, missing parent directories, and out-of-root paths. Parent directories must already exist and be exclusively service-owned; JavaScript path checks cannot defeat a hostile process replacing ancestor directories concurrently. A uniquely named exclusive partial is streamed and size/SHA-verified, fsynced, then hard-linked into the destination without overwriting anything. Filesystems without hard-link support fail closed. Only this operation's random partial is removed. Existing matching files are hashed and reused; mismatching files remain untouched. Concurrent identical in-process requests share hydration work. The external lease is held through the awaited consumer callback.

**HTTP lifecycle warning:** do not return a readable stream or `Response`/`NextResponse` directly from the callback. Response construction completes before its body is consumed. `openLeasedMediaStream` is the HTTP adapter: it resolves stream/size for response construction while retaining the lease until readable completion, error, or cancellation. FFmpeg and approval hashing should await their complete operation inside the callback. No eviction is enabled.

`DriveClient.streamFileContent(exactId, maxBytes)` performs bounded streaming with cancellation on early consumer exit, without mid-stream retries, buffering, or provider writes. The materializer verifies the supplied immutable content hash independently. Source authorization and trusted revision selection remain the caller's responsibility.

`withTutorialMedia(db, {jobId, kind, path, expectedContent?}, options, consume)` resolves missing bytes only from an uploaded `tutorial_job` artifact with matching job/kind/exact original path and non-null verified ID/SHA/size. Existing bounded regular local files remain usable even when not yet archived. Optional expected approval bytes are checked under the consumption lease, preventing a different local/archive revision from being substituted after review verification. The default lease uses a transaction-scoped PostgreSQL advisory lock: locks, archive lookup, and Drive settings/secret reads all use the **same pinned transaction**, never reentering the global pool while holding its connection. PostgreSQL releases locks on transaction end.

Use `withTutorialMediaSet` for multiple assets: it acquires unique canonical path locks in sorted order on one transaction and passes paths in original request order. Pass `options.transaction` when an approval transaction already exists; Hub approval capture and verification do this. Do not nest standalone default wrappers and consume extra pool connections. Streams still hold one connection until completion/cancellation, so configure bounded concurrency. Regression tests run ten parallel missing-file requests through a simulated single-connection pool and verify that no global query or nested connection acquisition occurs. Injected custom lease ports remain responsible for their own connection discipline.

Hub manual video download, tutorial thumbnail image reads, family approval capture, and publication approval verification now use the wrapper. Authorization precedes artifact lookup. Video reads are capped at 8 GiB and thumbnail reads at 32 MiB under `LOCAL_MEDIA_ROOT`; adjust deliberately if legitimate assets exceed those limits. Existing directories are required. Other media consumers and all mutation paths still need the same lease discipline before eviction can be considered safe.

Worker translation and splicing use `withTutorialWorkerInputs` with a lazy singleton **dedicated media pool capped at two connections**. Ordinary job queries/status writes keep using the original pool and commit independently. Translation restores/leases the original recording before narration LLM/TTS calls and holds it through completion; thumbnail-copy-only requests do not need recording bytes. Splicing leases the source-owned recording and validates/leases local narration before any probes/FFmpeg. Child recording lookup uses the English source job ID. `kind: null` explicitly represents local-only narration: a missing file produces an actionable restore error without archive lookup or paid regeneration. These input leases are retained through the real consumer and released on success or failure. Existing status/retry and localization revision guards remain in place. No eviction is enabled.

Manual video downloads support `?inline=1` and validated single byte ranges, including suffix/open-ended ranges. The stream adapter returns `206` with bounded filesystem start/end reads and `Content-Range`; invalid, multi-range, and unsatisfiable requests return `416` with total size. Responses advertise `Accept-Ranges: bytes`. Approval and authorization checks remain before streaming, and the lease lasts until range-body completion/cancellation. Restoring an evicted file still verifies its complete immutable archive before serving a range; partial archive bytes are never treated as a verified full file.

## Review availability projection and remaining gaps

The final-review GET now returns `localAvailable`, `receiptRecorded`, `restoreEligible`, `archiveCurrentBytesVerified` (false: this projection does not rehash), and `availabilityReason`. A configured, exact-path uploaded/verified SHA/size receipt can make missing local media playable through the verified download path. Bare Drive IDs, pending states, missing SHA/verification, ambiguous receipts, different owner/job/kind/path, unsafe filesystem paths, and local size mismatches do not qualify. `inDrive` is retained only as a compatibility alias for **receipt recorded**, not proof that current local or remote bytes were just verified. Actual playback and approval still perform full verification where required. No per-refresh bulk video hashing or Drive calls occur.

The tutorial-scoped `/api/production/jobs/[id]/thumbnail/[thumbId]` now hydrates exact current thumbnail bytes under the shared lease, after ownership and polymorphic-subject checks. This complements `/api/thumbnails/image/[id]` for tutorial assets.

Tutorial recording GET now uses exact source-owner raw-recording hydration and body-lifetime leases. Narration and long-audio GET use local-only leased inputs (no invented archive kind), preserve ranged streaming/private revalidation, and release immediately for matching ETag304 responses. Raw preview preserves the existing10GiB upload ceiling and no-store behavior; upload/DELETE implementations were not changed. Narration is still **not eligible for eviction**, since it has no durable archive kind.

Still **not certified for eviction**: generic `/api/media/[...key]`; archetype image GET and persona/reference artwork; non-tutorial thumbnail image reads. Recording uploads, thumbnail regeneration/rendering, and other writers also require the shared lease protocol before automatic eviction could be enabled. Do not evict source files based solely on the review projection.

### Final-video-only opt-in: remaining blockers

Review, Studio completed-video preview, and activity records use the now-leased tutorial download endpoint. Hub publication approval verification/capture also holds media locks. The scheduled connector asset GET (`production/delivery/[id]/assets/[role]`) now rechecks exact approved hashes under a lease retained through body completion/cancellation. The worker's `tutorial-uploader-exchange` holds exact approved final-video and thumbnail leases through inspection, Drive transfer, verification, and bookkeeping. Its final job-row admission uses NOWAIT to avoid job/media lock-order inversion; contention is deferred without a failed receipt or provider writes. `automatic-scheduled-delivery` and `late-locale-publication` capture publication fingerprints inside media sets on their existing caller transaction, without acquiring another pool connection. Generic media URLs can still address tutorial media without participating in the protocol.

Final-video-only eviction can be implemented after remaining generic consumers are scoped through the tutorial wrappers, and final-video writers either use the same path locks or publish immutable new paths atomically. Restrict eligibility to exact `tutorial_job/final_video` verified revisions, exclude active production/replacement and raw/narration/library assets, retain durable history, and run cancellation/concurrent-writer/connector recovery tests first. A source-only verifier is not sufficient to enable runtime deletion. No eviction was enabled here.
